Quality protocol: milestone gates and evidence

Quality, not speed, is the stated objective. The skill instructs the lead agent to:

  • Plan, then doubt the plan: write measurable acceptance criteria and risks first, and revisit decisions when evidence contradicts them.
  • Work in milestones that each pass a verification gate (tests, regression checks, review, evidence, updated state files) before the next begins.
  • Use an independent reviewer at meaningful milestones and for a final review, briefed to compare the work with the requirements, find gaps and challenge assumptions. If the reviewer agent is missing, the report must say the review was not independent.
  • Label evidence as Verified, Partially verified or Untested for every criterion, and never claim a check that was not run.
  • Recover from failure by finding the root cause, making the smallest fix and re-running the failed check and regressions, never repeating an identical failed approach, and stopping a workstream after three failed attempts.
  • Meet a completion standard (requirements implemented, criteria verified, critical tests passing, journeys working, no known critical defects, accurate docs, disclosed limitations) before calling the project done.

This is an instruction system for the model, not a guarantee that the result is defect-free. Review the work yourself.

Security gate

For projects that handle authentication, user or personal data, payments, externally reachable APIs, file uploads, secrets, integrations or AI/LLM tools with side effects, the skill instructs the lead to involve security-engineer, a read-only, independent reviewer:

  • Architecture: a threat model for the design decisions the architect flags as security-sensitive.
  • Milestones: a security review of milestones that touch authentication, data access, input handling, integrations, secrets, deployment configuration or AI tool permissions.
  • Before completion: a final security review. Trivial projects get a short checklist instead of a forced review.

Findings are rated Critical, High, Medium or Low, with file and line evidence, an exploitation scenario and a minimal fix. A Critical finding blocks completion and cannot be accepted. A High finding must be fixed or explicitly accepted by you; an accepted High stays recorded as open residual risk, never as fixed. Medium and Low findings are tracked. A finding counts as fixed only with evidence from a re-check. Reports state whether they rest on static inspection, automated scanning or penetration testing (not performed unless explicitly authorized), and a clean scanner run is never reported as "secure". The agent only reads and reports: it does not edit files, touch production, run destructive tests or access external targets, and these limits are instructions, not technical guarantees.

Nine Claude Code subagents

Each subagent is a Markdown file in .claude/agents/ with valid Claude Code frontmatter. Subagents start with no conversation history and cannot ask you questions, so the lead gives each a precise brief and integrates its output.

Safety and approval controls

  • Ask first: destructive database operations, production deployments, spending money, exposing secrets, deleting important data, irreversible external actions (including pushing and opening pull requests), and major product-direction changes.
  • Independent review required for non-trivial changes. If the reviewer agents are not installed, the delivery report must say no independent review took place.
  • Git: instructed to work on an auto-builder/<slug> branch; only the lead commits, by explicit path; your uncommitted changes are not to be committed; nothing is to be pushed. Review git log and the diff yourself.
  • Explicit invocation only: disable-model-invocation: true means Claude never starts the skill on its own.
  • No permission bypass. Use Claude Code permissions and sandboxing as the enforcement layer; the skill's rules are instructions to the model.

Safe installers

install.sh (Linux, macOS, WSL, Git Bash) and install.ps1 (Windows PowerShell) install for one project or all projects. They support --dry-run, never overwrite your files unless you pass --update (which keeps numbered backups), refuse to replace symlinks, and report stale files from older versions. See the installation guide.

Optional hooks

Two opt-in hook scripts are included but never enabled automatically: protect-secrets.sh blocks edits to secret-bearing file paths, and verify-on-stop.sh runs your check command before Claude finishes, with bounded retries and a timeout. Limits: the first does not cover Bash or Read, and the second is a strong nudge rather than an absolute gate.

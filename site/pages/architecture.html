Architecture: one lead agent, nine Claude Code subagents

Your main Claude Code session is the lead. It owns planning, integration, git and the final report. Subagents do bounded, independent work and report back.

Flow

{{PHASE_LIST}}

After phase 4 an optional Checkpoint A asks for your approval when a consequential choice is involved. Phases 5 to 7 repeat per milestone: each milestone must pass a verification gate before the next starts. The loop ends when the completion standard is met, a bound is hit, or a blocker needs you. The security gate runs alongside: a Critical finding blocks completion and a High finding needs a fix or your explicit acceptance.

Agents and permissions

{{AGENT_TABLE}}

Routing: product-manager for scope, researcher for current external facts, architect for design critique (and for flagging security-sensitive decisions), the three engineers for implementation, security-engineer for threat modeling and security review where the project warrants it, and qa-engineer plus critical-reviewer for independent verification. Security findings are owned by security-engineer; QA validates behavior and security regression tests; the critical reviewer judges overall quality. The lead spawns only what a task needs.

State files

Project memory lives in files, not in the conversation: docs/auto-builder/ holds PROJECT.md, REQUIREMENTS.md, ARCHITECTURE.md, TASKS.md, TESTING.md, DECISIONS.md, PROGRESS.md (a running log) and, where they apply, SECURITY-REVIEW.md (threat model, findings register and gate status) BROWSER-QA.md (browser test evidence) and LESSONS.md (project lessons, plus proposals that only you can apply), created from templates only as the project warrants and never overwritten. TASKS.md also holds the milestone gate table and the Verified / Partially verified / Untested state of every acceptance criterion. Stable facts such as build commands may be proposed for your project's CLAUDE.md.

Parallel work rules

  • Parallelise only independent work, after shared interfaces are fixed.
  • Every implementer gets an explicit list of files it owns. After integration the lead checks git diff --stat against it.
  • Only the lead commits, installs dependencies and edits lockfiles, shared config and state files.
  • Worktree isolation is an exception with caveats (needs a git repo; a fresh worktree may lack your unmerged work); see parallel-work.md.
